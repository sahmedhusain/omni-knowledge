# Guidely System Architecture Technical Specification

This document details the internal workings of the Guidely RAG (Retrieval-Augmented Generation) copilot pipeline.

## 1. Technical Stack Details
Guidely's application is divided into two primary systems:
- **Backend Service**: Built on **FastAPI** (Python 3.9+). It exposes endpoints for document ingestion, FAISS searches, and metrics logging. It connects to an SQLite database.
- **Frontend App**: Built on **React** (Vite + TypeScript + Tailwind CSS v4). It features a dark-mode glassmorphic interface with interactive citation overlays and circular metric widgets.

## 2. Ingestion and Text Chunking Pipeline
When a document is ingested via `/api/documents/upload`:
1. The document parser reads the file contents and decodes them to UTF-8.
2. The `Chunker` splits the document into smaller semantic text blocks.
3. Chunks are sized at **800 tokens** with a sliding overlap of **100 tokens** to prevent context loss at chunk boundaries.
4. Each chunk's checksum (MD5) is calculated and saved in the SQLite `chunks` table alongside the parent file reference.

## 3. Local FAISS Vector Store Index
Guidely uses the Facebook AI Similarity Search (FAISS) library to perform local vector storage and nearest-neighbor search.
- **Index Type**: We use `IndexFlatL2` which computes the L2 Euclidean distance between the query vector and all chunk vectors.
- **Mappings**: Because FAISS does not store metadata (such as document name or text content), we maintain an array of SQLite chunk IDs in `mappings.json` which maps directly to the rows in the FAISS float matrix.
- **Rebuilding**: Adding or deleting documents triggers a full rebuild of the FAISS index by compiling all active chunk vectors from the SQLite database.

## 4. Embedding Cache Database Schema
To reduce external API call latencies and fees, we maintain a persistent cache in SQLite (`embedding_cache` table):
- Columns: `checksum` (text hash, primary key) and `embedding` (serialized float array).
- Before calling OpenAI or Gemini, the system queries the cache. On a hit, it deserializes the JSON string to a float array, resulting in **100% cache hits** for unchanged texts.

## 5. Telemetry Tracking
All search queries and indexing runs log their latency, hit rates, exceptions, and retrieved passage details into the `query_logs` and `indexing_logs` database tables.
- **Median Latency**: Optimized to remain under **3.0 seconds** (typically ~850ms warm cache).
- **P95 Latency**: Optimized to remain under **5.0 seconds** (typically ~1.8s).
- **CSV Export**: The endpoint `/api/metrics/export/csv` generates downloadable query logs for system analytics.
